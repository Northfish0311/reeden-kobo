# Kindle 风格翻页动画：本地审计与离线优化

日期：2026-11-02。结论适用于本地 Clara Colour 393 开发实现，不代表公开 v0.7.4 已包含动画，更不代表本轮实验已经取得实体视觉提升。

## 范围和版本保护

- 审计先读取原工作区、未提交修改和旧实机日志，没有从远端重新实现。
- 原公开代码基点为 `d21ae018457854e3e757cd8fbb74927ac6a1e980`。
- 将完整本地开发状态保存为 `local/animation-baseline-20261102`，提交 `afac871ce4c1a2ac5565780382d81de5f99bd87a`。其中包含之前未提交的动画、夜间彩字和 Wi-Fi 工作。
- 实验位于独立工作树、分支 `experiment/animation-timing-20261102`。原 `main` 的文件、暂存区和未提交状态保留；原预编译文件也没有被实验产物替换。
- 本轮没有连接 Kobo，没有安装、启动或写入实体设备，没有修改官方 Reeden 二进制、内核或固件，也没有推送或发布。

证据分级：**代码事实**可由基线源码确认；**历史测量**来自已有设备日志，不是本轮测量；**推测**是需要进一步验证的机制解释；**未测**不能写成改善结果。

## 当前刷新链路

```text
evdev 触摸 → input.c 坐标转换 → Flutter 官方阅读逻辑
    → ireader_epdc.armPageTurn(forward, vertical, speedBits)
    → display_arm_page_turn：保留一个 2.5 秒有效的语义指令
Flutter 软件渲染回调 → pending（BGRA）
    → display_deadline：40ms 合帧；80/140ms 刷新间隔门限
    → refresh_plan：差异、颜色、夜间、清屏、区域对齐
    → 等待上次更新 → 必要的全局反相变更
    → 将整张最终图像写入 framebuffer（RGBX 或互补灰阶）
    → N 次局部 SEND_UPDATE + 每次 WAIT_SUBMISSION
    → 等待全部已接受 marker 的 WAIT_COMPLETE
    → committed / 计数 / 解锁 → 主循环继续处理输入与任务
```

核心模块：`src/host.c` 的通道与主循环，`src/input.c` 的触摸转换，`src/display.c` 的缓冲、提交与等待，`src/refresh_policy.c` 的区域/波形判断与条带计算。实验新增 `src/turn_timing.c/.h`；原波形选择没有更换。

## 十项审计结论

| 问题 | 结论与证据等级 |
|---|---|
| 1. 如何实现动画？ | **代码事实**：同一张最终书页按矩形条带逐个更新。没有移动页面纹理、生成中间混合帧或调用 Kindle 原生 Swipe。官方通道名称虽然包含 iReader，Kindle 官方 runner 也使用该接口。 |
| 2. 模式和波形？ | **代码事实**：动画是 `UPDATE_MODE_PARTIAL=0`，日间 raw waveform `8`、夜间 `9`，`flags=0x8000`（CFA_SKIP），dither=0。普通刷新用 mode=1；它不等同于“必然整屏白闪”。日间普通/清屏为 4/2，灰阶夜间为 9/8，彩色为 11/10 + CFA G2 `0x600`。 |
| 3. 分段数量？ | **代码事实**：快/普通/慢分别为 16/24/32 段，原最小间隔为 6/8/10ms，数量与间隔同时增加。1072px 横向 16 段的宽度为 64 或 80px；24 段、32 段均主要落在 32/48px 对齐宽度上。名义首末提交跨度至少为 90/184/310ms，并非真实整次翻页耗时。 |
| 4. 是否独立请求？ | **代码事实**：每段一个 36 字节 HWTCON 请求、独立递增非零 marker，随后等待该 marker 的提交。`refreshes` 每整次页面事务加一，不能把这个计数当成 ioctl 次数。 |
| 5. 驱动是否合并？ | **未证实**：独立 ioctl/marker 只证明用户态发出独立请求。WAIT_SUBMISSION 用来降低 MDP 合并机会，但不是“面板一定独立显示每条”的证据。需要设备任务/碰撞诊断（如果驱动提供）以及实拍时间线；本轮没有读取设备。 |
| 6. 旧、新帧如何管理？ | **代码事实**：`committed` 保存旧逻辑 BGRA 图像，`pending` 保存最新 Flutter 图像，各约 5.92MiB。动画开始前 framebuffer 写入整张新图，整轮所有条带读取同一张图。旧内容在尚未更新区域由物理面板保留，没有硬件双缓冲切换或 old/new 插值。 |
| 7. framebuffer 是否过早覆盖？ | **代码事实**：当前内部链路在写像素前等待上次更新，条带提交后等待全部已接受 marker，并持有 display mutex，未发现下一帧提前覆盖在途 framebuffer 的内部路径。不能据此排除其他进程/驱动故障。普通路径存在另一个边界问题：逻辑 committed 在最终等待成功前就更新；等待失败后会退出，但缓存状态先前进了。这不是发现了实际 framebuffer 撕裂。实验宿主已统一改成完成成功后才前进逻辑缓存，默认成功刷新参数不变。 |
| 8. 等待是否正确？ | **代码事实**：提交失败时只等待已接受请求，不等待被拒绝的 marker；结束前逐一等待完成。基线的完成记账会把最后一个被拒绝 marker 也记作 completed；已接受任务仍已等待，这不是漏掉在途请求，但记账不够准确。实验宿主改为独立记录最后一个实际接受的 marker，并只等待有效接受的请求。另外发现基线普通 SEND 被拒绝后下一轮也可能等待被拒绝的编号；该错误路径已统一修正。完成 ioctl 本身失败时只能停止继续绘制，不能宣称已恢复硬件。 |
| 9. 时序是否均匀？ | **代码事实**：原实现以“上一条实际提交时间 + 最小间隔”安排下一条，不是固定空间速度的整段时钟。宽度不同却同间隔，理论推进速度也不同。**历史测量**只保留首末跨度和最小间隔，不能还原每条最大间隔、抖动或驱动执行时间。 |
| 10. 与 Kindle 原生 Swipe 的差异？ | **公开源码事实**：Kindle MTK 请求有 `swipe_data.direction/steps`、专用 enable flag；FBInk 对动画请求使用 AUTO，内核再选择 REAGL/P2SW 等内部路径。当前 Kobo 36 字节接口没有对应 Swipe 参数；不能把 Kindle 的 flag、结构体或 P2SW 编号直接传给它。 |

基线还有一个与响应直接相关的事实：整个 `flush()` 在平台主线程持锁执行，包含 sleep、所有提交与完成等待；输入读取和 Flutter 平台任务在该函数返回后才继续。渲染回调也会等待同一把锁。2.5 秒 arm 槽只有一个，不是动画请求队列。此轮保留这一结构，**没有把它称作异步显示系统**。

## 历史实机数据能说明什么

数据源为已有本地 `work/display076/fine-device-accepted.log`：白底灰阶、快档 16 段，8 次前翻、2 次后翻。不是本轮重测。

| 指标 | 最小 | 平均 | 最大 |
|---|---:|---:|---:|
| 第一条到最后一条提交 | 147.0ms | 163.61ms | 178.5ms |
| `flush` 的 `work_ms` | 589.3ms | 602.30ms | 642.7ms |

两项均值相差约 438.69ms，但这部分混合了策略计算、拷贝、首条之前和末条之后的硬件等待等，**不能全部归因于屏幕响应时间**。`work_ms` 不包含完整触摸排队、Flutter 渲染和此前合帧等待，也不证明肉眼已稳定。旧日志不足以给出“触摸至稳定”的端到端时延。

已有用户反馈确认细分快档“更连续了，效果和速度可以接受”；之前也确认夜间稀疏彩字闪烁缩小、颜色正常。上述反馈支持保留基线，不意味着已经达到 Kindle 原生效果。

## 影响效果的原因，按证据充分程度排序

1. **架构确定**：整高矩形条带只是在新旧静止页面之间切换，不具备 Kindle 内核 Swipe 的内部阶段调度。条带边缘本来就是直线，颜色/灰阶响应尚未完成时，相邻列处在不同阶段，容易显出竖条。后半句的显著程度仍需视频验证。
2. **阻塞确定**：主线程和渲染回调在整轮等待期间不能正常推进。历史函数耗时约 0.6s，连续操作会积压；这比只讨论 6ms 的 sleep 更关键。
3. **参数耦合确定**：增加分段同时增加间隔；24→32 段受 16px 对齐限制，条带并没有同比变细，却增加了请求数量和名义周期。不是分段越多越好。
4. **空间速度不一致确定，观感影响待测**：64/80px 共用间隔，或 32/48px 共用间隔，理论局部推进速度分别相差 25%/50%。驱动和调度耗时还会叠加，旧日志无法还原实际抖动。
5. **硬件响应的影响合理但未量化**：相邻条带的电子墨水变化会跨越较长时间。提交间隔不是可见刷新完成时间；连续刷新是否被合并、LUT 竞争是否产生停顿，尚无当前设备的新测量证据。
6. **颜色和夜间是独立边界**：CFA 需要保留色彩处理；把彩页强行按灰阶扫动可能换来颜色异常。当前灰阶动画绕开彩色、旧色擦除、主题反转、清屏及封面；稀疏夜间彩字继续使用原分区方案。密集彩色和主动清屏仍可闪烁，本轮没有用额外全刷掩盖问题。

方向方面，`forward`/`vertical` 来自官方阅读逻辑，而非重新猜触摸方向；横向 forward 从右向左更新，反向相反。触摸有 swap+mirrorX 转换，另有可选反转环境变量；动画直接使用 framebuffer 的原生坐标。当前只对已测的 1072×1448、rotate=3 启用 timed 实验，其余几何回退普通刷新。RTL、纵向、其他旋转仍需实体反馈，不能由横向 mock 测试推断。

## 三种候选方案

| 方案 | 预期改善和模块 | 内存/CPU | 风险与实机要求 | 本轮选择 |
|---|---|---|---|---|
| A：改进现有条带时序 | `turn_timing` + `display`；把数量与总周期分开，按实际像素推进距离给出绝对目标时刻；迟到后保留最小实际间隔，避免追赶性连发；加入日志 | 不增加整帧缓冲；约数 KiB 的事务/trace 栈空间，trace 输出有额外开销 | 均匀用户态调度不等于均匀面板响应；周期过短会重新合并/丢失扫动感，过长会拖慢。需要同页 A/B | **已实现，默认关闭** |
| B：改进缓冲与显示队列 | 在独立显示执行器中固定一张目标快照，让平台线程继续接收输入；最新请求代替积压动画，在完成屏障之后取消或切换；涉及 host/display/power/cover 生命周期 | 通常再加一张约 5.92MiB 目标快照及线程/通知开销；减少平台线程等待，但硬件耗时不消失 | 覆盖、休眠、退出、渲染线程间竞态明显增加；需要真机压力测试。有限在途窗口也可能更慢 | 仅实现可选在途上限和安全记账；**未接入显示线程/新帧队列** |
| C：接近原生硬件 Swipe | 先只读确认 Kobo 实际驱动是否公开对应能力，再考虑单请求硬件内部推进；不能仅因芯片同属 MTK 就假设支持 | 若有可用接口，可减少用户态提交；当前无法估算完整开销 | 已查 UAPI 未见等价 Swipe 参数。不得试未知 flag/波形，也不修改内核或固件 | **没有已证实的安全接入路径，未实现** |

选择 A 的依据是回退简单、不动波形、不增加完整图像副本，且能先补齐测量。B 对输入响应更有潜力，但不是本轮可以凭编译通过就替换的结构。C 不能用未经证实的驱动调用强行实现。

## 实际改动

- `src/turn_timing.c/.h`：受限参数、空间比例时序、抗追赶连发、结构化 trace。无环境配置时保留 stable；错误参数回到 stable 并给出说明。
- `src/display.c`：三种 profile；可选在途上限；合作式取消；所有已接受任务完成后才能普通刷新回退。普通路径统一在等待成功后才更新 committed；拒绝的 marker 不会成为下一轮等待目标。波形和 CFA 选择保持原逻辑。
- `src/input.c`、`src/host.c`、`src/kobo.h`：仅 trace 开启时记录 evdev read 返回的时间，以及 arm、首次/末次关联渲染回调。不是手指碰屏时间，也不包含已积压在 evdev 队列中的等待。
- `scripts/analyze-turn-trace.py`：逐事务解析 marker、区域、波形、提交/等待耗时、间隔 min/max/标准差和在途峰值；拒绝缺失 trace、缺少完成等待却声称成功等情况；强制标记 `mock` 或 `device` 数据。
- `scripts/test-turn-offline.sh`、测试文件：本机 ASan/UBSan 回归。macOS 的 framebuffer 字段模型仅供 mock 编译，**不验证真实内核 ABI**；ARM 构建仍使用 Linux 头文件及 36 字节断言。
- 构建脚本加入新模块；未替换发布目录里的预编译包。

`display_cancel_page_turn()` 是可供其他执行上下文调用的合作式取消 API，timed 也检查退出请求。当前主循环仍同步，**没有新增可在动画途中即时响应的 UI 取消按钮**；取消还必须等待已接受的硬件任务结束。本轮测试证明的是后端取消/回退契约，不能当作用户快速连点时的实体响应改善。

## 回滚

本轮设备没有变化，无须设备回滚。原工作区也无需还原，仍是用户原来的未提交版本。实验全部保存在独立分支/工作树；可停止使用它，保留 baseline 分支即可。

未来经单独同意部署实验宿主后：先退出阅读器，在电脑上去掉所有 `REEDEN_TURN_*` 启动参数即可回到该宿主的 stable 行为。若需要字节级退回，恢复部署前一并备份的宿主、检查程序、build-info 和 SHA256SUMS，校验后再启动；只回退其中一个文件会造成清单不一致。应保留 userdata/storage。不可在运行或休眠中覆盖程序。

## 最终判断

目前效果差距的确定原因是矩形分区的动画模型、阻塞的主线程链路及分段/间隔/像素宽度耦合；并没有证据把问题归结为 framebuffer 被覆盖，也不能断言驱动已经合并了刷新。

已经改进的是可选时序模型、参数可比性、观测能力、取消/错误回退和缓存与已接受 marker 的完成记账。尚未证明改善的是实体自然度、响应速度、残影和续航。Kobo 已公开接口没有被证实支持 Kindle 的原生 Swipe/P2SW 调度，这限制了直接复现，但并不能据此断言所有 Kobo 硬件都绝对做不到。进一步接近自然扫动有空间；是否更好，必须由同页 A/B 视频和现场反馈决定，不能用更多 ioctl 或编译成功替代。
