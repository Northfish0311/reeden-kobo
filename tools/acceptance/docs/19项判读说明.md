> **权威验收口径**：`docs/实机验收清单-v0.7.9-community.4.md`（全量基线）+ `docs/实机验收清单-v0.7.9-community.5.md`（差异集）。两者与本文件冲突时，以那两份为准。
> **路径约定**：文中 `src/…`、`scripts/…` 指**仓库根目录**下的设备端源码（`src/host.c`、`scripts/power.sh` 等），不是 `tools/acceptance/scripts/`；工具脚本一律写全为 `../scripts/Collect-Evidence.ps1` / `../scripts/Check-Evidence.ps1`。`E:\` 是本机 Kobo 挂载示例，按实际盘符替换。

> **用法**：逐条按编号核对，编号与 `Check-Evidence.ps1` 的检查项 ID 一一对应；同目录的 `判读依据-源码静态审查.md` 引用同一编号。第 0 章为人工前置（脚本不判读）；第 1~6 章每项都可被脚本三态判读。

# 第 0 章 前置（人工，脚本不判读）

### 0.1 安全插拔
- **前置**：设备已装好 `.4`，Reeden 能正常启动。
- **操作步骤**：**先在 Kobo 上退出 Reeden 回到原生主页**，再插 USB；电脑上完成只读取证后，**等系统显示「安全弹出 / 安全卸载硬件」再拔线**。
- **期望现象**：Kobo 显示「已连接」，电脑出现 `E:\`；拔线后回到原生主页且书库/笔记完好。
- **看哪份日志 / 哪一行**：不适用（这是防写坏 FAT32 的操作纪律，不是代码行为）。
- **失败怎么办**：不要反复带电插拔重试（曾写坏 FAT32）。若弹出失败，先在电脑上关闭所有资源管理器窗口 / 杀掉占用进程，仍失败则重启电脑后再安全弹出。**禁止** `chkdsk`、禁止重算 `SHA256SUMS`、禁止改官方二进制。

### 0.2 日志时区换算
- **前置**：知道现场操作的北京时间，并**先在设备上核对一次 `date` 输出**（`power.sh` 用的是 `$(date)`，`run.sh` 未设 `TZ`，源码未强制 UTC；Kobo 默认通常为 UTC）。
- **操作步骤**：记录每一步的**北京时间**；按实机确认的偏移把日志时间换算成北京时间（通常为 +8 小时）。`host.c` 的 `wall=<epoch秒>` 是 `CLOCK_REALTIME` 绝对值，可作不受时区设置影响的锚点。
- **期望现象**：`power.sh` 的 `$(date)`、以及 `host.c` 的 `[power] phase=... wall=<epoch秒>` 都能与操作时刻对上。
- **看哪份日志 / 哪一行**：`power.log` 每行末尾的 `$(date)`，如 `[power] invoked arg=suspend Mon Nov 12 04:13:02 UTC 2026`；`current.log` 的 `[power] phase=cover-closed wall=1762927982 mono_ms=...`（`wall` 是 `CLOCK_REALTIME` 绝对 epoch 秒）。
- **失败怎么办**：先按实机确认的偏移（通常 ±8 小时）换算再判断「日志没出现」；别按北京时间直接搜，也别假定源码一定强制 UTC。

### 0.3 取证前不要重启 Reeden
- **前置**：准备做某一轮的合盖 / 水波纹取证。
- **操作步骤**：做完一轮操作后立刻跑 `Collect-Evidence.ps1`，**不要**为了「再看一遍」而退出重进 Reeden。
- **期望现象**：本轮日志留在 `current.log`。
- **看哪份日志 / 哪一行**：`run.sh` 每次启动执行 `mv -f current.log previous.log` 再 `: > current.log`。
- **失败怎么办**：若已重启，去 `previous.log` 找；脚本判读 `current.log` 时会自动合并 `previous.log`。

### 0.4 回退开关（人工手动，脚本绝不创建）
- **前置**：仅当合盖行为异常（误休眠、唤不醒、盖传感器误报）时才启用。
- **操作步骤**：退出 Reeden 回原生主页 → 插 USB → 在 `E:\.adds\reeden-kobo\userdata\` 下**新建空文件** `no-sleep-cover`（不要写内容）→ 安全弹出 → 下次启动生效；删除该文件恢复默认。
- **期望现象**：`current.log` 出现 `[cover] disabled by user preference`，电源键仍可用。
- **看哪份日志 / 哪一行**：`current.log` 的 `[cover] disabled by user preference`（`host.c:471`）；不再出现 `[cover] candidate event...` 与 `[cover] closed`。
- **失败怎么办**：**这是人工步骤，脚本绝不自动创建该文件**。若创建后仍异常，改用电源键并保留原始日志，不要用反复断电代替排错。

### 0.5 设备盘只读
- **前置**：两个脚本已就位。
- **操作步骤**：只用 `-OutDir` 指向本地目录（默认 `.\evidence`）。
- **期望现象**：`Collect-Evidence.ps1` 只打印 `[OK]`/`[MISS]`，`manifest.json` 写明 `never writes to the device volume`。
- **看哪份日志 / 哪一行**：不适用。
- **失败怎么办**：若脚本提示 `OutDir must NOT be on the device volume`，把 `-OutDir` 换到 C:/D: 上的本地路径。

### 0.6 设备未挂载时的空跑
- **前置**：当前 `E:\` 未挂载（系统只有 C:、D:）。
- **操作步骤**：直接跑一次 `Collect-Evidence.ps1`，确认优雅退出。
- **期望现象**：打印 `DEVICE NOT AVAILABLE - no evidence collected.` 与 `This is NOT an error.`，退出码 `0`，不生成空 evidence 目录。
- **看哪份日志 / 哪一行**：不适用。
- **失败怎么办**：若报别的错，检查 `-AppDir` 是否含中文引号/尾部空格；此步不应报错。

### 0.7 彩色水波纹实验开关（`.5` 可选，默认关闭）
- **前置**：已完成 `.5` 更新，且**普通阅读确认正常**；仅在想试彩色条带时才做。
- **操作步骤**：退出 Reeden 回原生主页 → 插 USB → 把 `E:\.adds\reeden-kobo\userdata\turn-profile` 的内容改成 `color`（无扩展名文本文件，升级时会保留旧值）→ 安全弹出 → 重开 Reeden → **阅读器内仍需开启水波纹**。改回 `stable` 关闭彩色实验；写 `off` 则关闭全部水波纹。
- **期望现象**：3.2 出现 `[color-turn] bands=... path=cfa wave=11 mode=1`（最多 8 段）；失败时出现 `[color-turn] incomplete; experimental color sweep disabled for this session`，本次运行回退普通彩色刷新。
- **看哪份日志 / 哪一行**：`current.log` → `[color-turn] bands=%u direction=%s vertical=%u path=cfa wave=%u mode=1; optical quality unverified`（`display.c:221`）/ `[color-turn] incomplete; experimental color sweep disabled for this session`（`display.c:217`）；`run.sh:139` 读 `turn-profile` 为 `color` 时导出 `REEDEN_COLOR_TURN=cfa`。
- **失败怎么办**：**这是实验功能**。分段可能更慢、有接缝或色偏，出现不适立即改回 `stable` 重开。`[color-turn]` 完成只证明**软件事务完成**，**不证明彩字不淡化、不证明光学效果**——淡色/接缝/残影必须肉眼对照同一页记录。彩色实验回退会让 3.2 判 `FAIL`，但**不等于**普通彩色刷新也失败。

# 第 1 章 优先级 1：合盖休眠（ID 1.1 ~ 1.5）

### 1.1 盖传感器被识别 / 启用状态明确
- **前置**：Reeden 已打开并完成首帧、拿到显示所有权；未创建 `no-sleep-cover`；**启动时保护盖必须是开着的**（见 1.2 的 `cover_seed` 说明）。
- **操作步骤**：打开 Reeden，随后取 `current.log`。
- **期望现象**：`current.log` 有 `[cover] candidate eventN SW_LID` 或 `[cover] candidate eventN internal KEY_F1`。
- **看哪份日志 / 哪一行**：`current.log`（或 `previous.log`）→ `[cover] candidate event%u SW_LID` / `internal KEY_F1`（`cover.c:cover_open`）。若传感器不支持：`[cover] no supported internal lid input; power key remains available`；若被人工停用：`[cover] disabled by user preference`（`host.c:471`）。
- **失败怎么办**：`no supported internal lid input` 表示本机没有受支持的内部盖传感器（面板会显示「传感器暂不支持」），**改用电源键**（第 2 章）或控制面板「立即锁屏」（5.3）；`disabled by user preference` 表示 0.4 的回退开关还在，删掉 `no-sleep-cover` 再测 1.2~1.5，否则这几项不适用。

### 1.2 合盖边沿被记录
- **前置**：1.1 已识别传感器；Reeden 停留在阅读页；**本轮的 Reeden 是在开盖状态下启动的**（`.5` 的 `cover_seed()`，`src/cover.c:57`，会把启动瞬间的盖子状态直接 adopt 为「已上报」，并清掉去抖定时器；因此**合着盖启动不会产生 `[cover] closed`**，那是「启动状态」而不是「边沿事件」）。
- **操作步骤**：保持 Reeden 打开，**合上磁吸保护盖**，等约 3 秒。
- **期望现象**：屏幕灭、前光灭；日志出现合盖边沿。
- **看哪份日志 / 哪一行**：`current.log` → `[cover] closed` 以及 `[power] phase=cover-closed wall=<UTC epoch秒> mono_ms=<ms>`（`host.c:477`，`power_trace` 输出）。**开盖/合盖边沿在 `current.log`，不在 `power.log`**。
- **失败怎么办**：无 `[cover] closed` → ① 先确认是不是**合着盖启动**的（`.5` 设计如此，开盖再合盖即可）；② 检查 1.1、保护盖磁铁位置、是否被 0.4 停用；③ 边沿有 150 ms 去抖（`cover.c:observe`），别瞬间开合。若 `previous.log` 里才有，说明取证前重启过（见 0.3）。

### 1.3 锁屏、关前光、引擎保留
- **前置**：1.2 合盖已发生。
- **操作步骤**：合盖后保持 2 秒以上，观察屏幕与背光。
- **期望现象**：屏幕熄灭、前光熄灭，Reeden 进程未退出（开盖后回原页）。
- **看哪份日志 / 哪一行**：`current.log` → `[power] phase=locking wall=... mono_ms=...`、`[power] screen locked; engine retained`（`host.c:set_sleep(true)`）；约 1.4 秒后前光写 0（同段逻辑），有自定义锁屏图时另有 `[sleep-cover] displayed Reeden image channels=N`，无图时 `[sleep-cover] not registered; keeping current page`。
- **失败怎么办**：**`.5` 起锁屏图失败不再取消休眠**。看到 `[sleep-cover] image not confirmed; keeping current page, continuing to suspend`（`host.c:500`）表示保留当前画面、继续走锁屏与休眠，**属设计行为，不要当故障**；把「自定义锁屏画面」关掉或重设可以恢复正常的封面显示。`.4` 时代此处是 `image not confirmed; cancelling suspend` 并 `set_sleep(false)` 回到阅读——**该行为已废弃，`.5` 不再产生这行**，别拿它当判据。显示完成状态不明（`display_wait` 失败）时仍会停止绘制并走错误恢复。

### 1.4 内核休眠请求与返回（本优先级核心）
- **前置**：1.3 已锁屏；**设备未在 USB 充电**（充电/满电/外部电源读数 on 会走供电保护，只锁屏不进内核休眠，属设计行为）。
- **操作步骤**：合盖后静置 ≥ 30 秒，再开盖，随后取证。
- **期望现象**：`power.log` 出现一次完整的 `[power] invoked arg=suspend` → `[power] entering mem` → `[power] mem returned=0`。
- **看哪份日志 / 哪一行**：`power.log`（`power.sh`）→
  `[power] invoked arg=suspend <UTC date>`（第 7 行，实参由 `power_worker_start()` → `power_worker_command(path,"suspend")` 固定传入）；
  `[power] phase=preparing uptime=N pid=N <date>` → `[power] phase=suspended uptime=...`；
  `[power] entering mem <date>`（第 136 行）；
  `[power] phase=resuming uptime=...` → `[power] mem returned=0 <UTC date>`（第 142 行，`=0` 才算成功）。
  **注意**：`power.sh` 还会以 `restore` / `native` 实参被调用，日志会是 `invoked arg=restore` / `=native`，**只有 `=suspend` 是休眠尝试**。
- **失败怎么办**：
  - 有 `invoked arg=suspend` 但**没有** `entering mem` → 看兜底行：`[power] screen-only: supply guard battery=... external=...`（供电保护，`exit 3`）、`[power] display did not become idle`（显示忙，`exit 75`）、`[power] existing alarm: suspend cancelled`（`exit 2`）、`[power] Wi-Fi could not be suspended`（`exit 4`）。**这些不是故障**，拔掉 USB、确认在放电、等显示空闲后重测；脚本会判 `NEED-EVIDENCE` 而不是 `FAIL`。
  - `mem returned=1`（或其它非 0）→ 明确失败，保留 `power.log` 全文。
  - `[power] short mem return after Ns; wake source unknown`（`exit 76`）/ `[power] still locked; one guarded retry in 8s`（`host.c:445`）→ 适配层会在 8 秒后**有守卫地重试一次**，用户唤醒优先；观察第二次 `entering mem`。
  - 完全找不到 `invoked arg=suspend` → 检查 1.1/1.2，或 `state/power-screen-only` 标记是否存在（`host.c:513` 存在时根本不启动 `power.sh`）。

### 1.5 开盖恢复
- **前置**：1.4 已发生（或至少 1.3 已锁屏）。
- **操作步骤**：**打开保护盖**，短等 1~3 秒，看是否回到原阅读页、前光是否恢复。
- **期望现象**：屏幕亮、回到原书原页，前光亮度与合盖前一致。
- **看哪份日志 / 哪一行**：`current.log` → `[cover] opened`、`[power] phase=cover-opened wall=... mono_ms=...`（`host.c:482`）；若当时 helper 还在跑，另有 `[power] wake requested; waiting for hardware restoration`（开盖/按键唤醒置 `power-cancel`）；恢复完成有 `[power] phase=restoring-reader ...`、`[power] resumed same engine and book`、`[power] phase=reader-resumed ...`。`power.log` 里可能有 `[power] Wi-Fi resume deferred while cover remains closed`（盖仍关时延后 Wi-Fi 恢复）。
- **失败怎么办**：唤不醒先用**短按电源键**（第 2 章）；仍不行启用 0.4 回退开关 `no-sleep-cover`，改用电源键，并保留日志。检查是否有 `[power] helper wait failed: ...; returning to native UI`（helper 异常，会退回原生 UI）。

# 第 2 章 优先级 2：电源键休眠（ID 2.1 ~ 2.2）

### 2.1 短按电源键锁屏并调用 `power.sh suspend`
- **前置**：Reeden 在阅读页、未接 USB 充电。
- **操作步骤**：**短按**电源键一次，等 ≥ 30 秒。
- **期望现象**：屏幕灭、前光灭；`power.log` 出现 `invoked arg=suspend` 及后续休眠返回。
- **看哪份日志 / 哪一行**：
  `current.log` → `[power] exclusive power key acquired`（启动时独占 `/dev/input/event2`）、`[power] key release`（`host.c:557`）、`[power] screen locked; engine retained`；
  `power.log` → `[power] invoked arg=suspend <UTC date>` → `[power] entering mem` → `[power] mem returned=0`。
  **这是任务点名的验收入口**：「`logs/power.log` 是否出现 `invoked arg=suspend` 及后续休眠返回」。
- **失败怎么办**：没有 `key release` → 检查是否被 `no-sleep-cover` 影响（不会，它只关盖检测）、是否按键太短被吞；有 `key release` 但无 `invoked arg=suspend` → 按 1.4 的兜底清单排查（供电/显示忙/`power-screen-only`）。**`invoked arg=restore` / `=native` 不算休眠尝试**。

### 2.2 再按电源键唤醒
- **前置**：2.1 已锁屏。
- **操作步骤**：再**短按**一次电源键。
- **期望现象**：亮屏、回到原书原页，前光恢复。
- **看哪份日志 / 哪一行**：`current.log` → `[power] key release`；若 helper 仍在跑会有 `[power] wake requested; waiting for hardware restoration`；恢复后有 `[power] resumed same engine and book`、`[power] phase=reader-resumed ...`。`power.log` → `[power] mem returned=0` 与 `[power] phase=resuming uptime=...`。
- **失败怎么办**：只有 `[power] screen stays locked; no more retries for this lock` 说明本次锁屏已用尽那一次 8 秒重试，属设计行为；再按一次或退出重进。若 `mem returned` 非 0，按 1.4 处理。

# 第 3 章 优先级 3：水波纹（ID 3.1 ~ 3.3）

### 3.1 `armPageTurn` 请求到达适配层
- **前置**：Reeden 阅读页，已拿到显示所有权。
- **操作步骤**：在 Reeden 里翻页若干次（前翻、后翻都做），随后取证。
- **期望现象**：`current.log` 出现 `[page-turn] arm ... accepted=1`。
- **看哪份日志 / 哪一行**：`current.log`（或 `previous.log`）→ `[page-turn] arm type=%d forward=%u vertical=%u steps=%u accepted=%u`（`host.c:255`，`armPageTurn` 分支）。`accepted=1` 表示 `display_arm_page_turn()` 接受了请求（已获取显示所有权、`committed_valid`、steps 在 2..上限之间）；`steps` 由 `speedBits` 映射为 16 / 24 / 32。
- **失败怎么办**：**无 `arm` 行 = Reeden 设置组合问题，不是适配层问题**。按 3.3 逐项核对设置；同时确认 `capabilities` 里 `armPageTurn=true`（`host.c:242`）。`accepted=0` 表示当时未拿到显示所有权/帧未提交，等首帧完成后再翻页。

### 3.2 水波纹动画真的下发
- **前置**：3.1 `accepted=1`；`turn-profile` 不是 `off`（若在试 `.5` 彩色实验，见 0.7）。
- **操作步骤**：连续翻 3~5 页，肉眼确认分条扫动效果与残影情况，随后取证。
- **期望现象**：`current.log` 出现 `[page-turn] bands=...`（灰阶路径）**或** `[color-turn] bands=...`（`.5` 彩色实验路径，最多 8 段）；必要时还有 `[page-turn] submissions=...`。
- **看哪份日志 / 哪一行**：`current.log` → 灰阶：`[page-turn] bands=%u direction=%s vertical=%u night=%u path=%s wave=%u mode=%u`（`display.c:196`）；彩色（`.5`）：`[color-turn] bands=%u direction=%s vertical=%u path=cfa wave=%u mode=1; optical quality unverified`（`display.c:221`）；计时：`[page-turn] submissions=%u span_ms=%.1f min_gap_ms=%.1f`（`display.c:172`，条带数 >1 且计时/间隔模式时）。
  **`accepted=1` 只代表请求到达，不等于动画画出去了**——`flush()` 里还要求：非清屏、非彩色页、非夜间反转切换、`xres>=160`、`turn-profile != off`（TIMED/reagl 还要求 1072×1448 rotate=3）。走彩色实验时另要求 `turn-profile=color`（`REEDEN_COLOR_TURN=cfa`），彩字/彩色高亮/背景图保留原始 RGB，不进灰阶扫动。
- **失败怎么办**：
  - 有 `accepted=1` 但无任何 `bands=` → 先看 `userdata/turn-profile`：值为 `off` 时源码直接 `animate=false`（**预期无动画**）；彩色页/清屏/夜间反转切换也会走普通刷新路径，属预期。
  - `[color-turn] incomplete; experimental color sweep disabled for this session` → 彩色实验本段失败、已回退普通彩色刷新并**本次运行关闭彩色**；脚本判 3.2 `FAIL`（它确实没画出去）。改回 `stable` 或重开再试，并记录是否伴随 `[display-sequence]` 失败。
  - `[page-turn] invalid experiment configuration; stable profile retained`（`display.c:62`）→ `turn-profile` 值非法，已回退 `stable`。
  - `[display-sequence] cancelled; restoring normal page update` / `submission failed; restoring normal page update` → 驱动提交失败，保留日志。
  - 官方说明：本版**不宣称解决水波纹残影、彩字淡化或高亮规则卡死**；`[color-turn] bands=` 里的 `optical quality unverified` 就是这句话的缩写，实机效果必须肉眼对照记录，不能凭日志判「彩色已验收」。

### 3.3 水波纹设置组合（人工确认项）
- **前置**：能进入 Reeden 阅读设置。
- **操作步骤**：确认三项同时成立：① 普通「翻页动画」= **无动画**；② 「水波纹翻页」= **开**；③ 阅读时确实触发了 `armPageTurn`。
- **期望现象**：3.1 出现 `arm ... accepted=1`。
- **看哪份日志 / 哪一行**：无对应自动日志，脚本固定输出 `NEED-EVIDENCE`，需人工在清单上勾选。依据：`docs/翻页动画AB测试流程.md` 明确「普通翻页动画设为无动画，水波纹功能保持开启，使三组收到相同的语义 arm 指令」；`docs/releases/v0.7.5.md` 建议「先选快档，并将普通翻页动画设为无动画」。
- **失败怎么办**：三项缺一即不会有 `arm` 行，**不要判定为适配层缺陷**。逐项改设置后重测 3.1；`userdata/turn-profile` 若为 `off` 会连动画一起关掉，注意区分。

# 第 4 章 三个验收入口（ID 4.1 ~ 4.3）

### 4.1 首帧耗时：`logs/launcher.log` 的 `first frame took`
- **前置**：任何一次冷启动 Reeden。
- **操作步骤**：从原生主页启动 Reeden，记录启动到出画面的秒数，退出后取证。
- **期望现象**：`launcher.log` 有 `[launcher] first frame took Ns`，N 与手表/秒表实测接近。
- **看哪份日志 / 哪一行**：`launcher.log` → `[launcher] first frame ready; hardware handoff authorized` 紧接 `[launcher] first frame took Ns`（`run.sh:166-167`）。超时反证是 `[launcher] no first frame in 20s; Nickel was never paused`（`run.sh:151`，退出码 20）。同文件还应有 `[verify] manifest unchanged and every file present; skipped full hashing`（`run.sh:85`，校验缓存命中，写在 `launcher.log` 而非 `install-verification.log`）。
- **失败怎么办**：出现 `no first frame in 20s` → 明确失败，检查 `install-verification.log`（路径见速查表）是否有校验失败、是否从 KOReader 直接启动（`run.sh` 会拒绝并提示 `Exit KOReader and launch from NickelMenu`）。N 偏大先确认是不是本次没走校验缓存（首次/每周一次全量 SHA256 会明显变慢）。

### 4.2 退出后 `Kobo eReader.conf` 的 `FrontLightLevel` 与观感一致
- **前置**：在 Reeden 里**明确调过一次非零前光亮度**，然后**正常退出**回原生主页。
- **操作步骤**：调亮度 → 正常退出 Reeden → 回原生主页看前光观感 → 安全弹出 USB → 取证。
- **期望现象**：原生主页前光观感与 Reeden 里选的一致；`Kobo eReader.conf` 的 `[PowerOptions]` 段有 `FrontLightLevel=` 行。
- **看哪份日志 / 哪一行**：`E:\.kobo\Kobo\Kobo eReader.conf` → `[PowerOptions]` 段内 `FrontLightLevel=<N>`（`recover.sh:70/80/87`）；`launcher.log` → `[recovery] Nickel brightness updated to N`（`recover.sh:90`，**写在 `launcher.log`，没有独立的 recovery 日志**）；失败反证 `[recovery] Nickel brightness update failed; hardware value kept`（`recover.sh:93`）。
  **刻度提醒**：Reeden 用感知刻度（如 11），sysfs / Nickel 用硬件刻度（如 46），**数字不同是正常的，只要观感一致**。脚本只提取原始行、不做刻度换算。
- **失败怎么办**：
  - 没有 `Nickel brightness updated` 且 `FrontLightLevel` 未变 → 多半是**没有「正常退出且用户选了非零亮度」**：`recover.sh:sync_nickel_light` 要求 `clean_exit=true` + `choice_light` 有效且 >0 + 硬件读数等于该选择值 + 配置文件存在且非符号链接。异常退出（崩溃、双上角长按强制退出）会恢复启动快照，**这是设计行为，不是故障**。
  - `Nickel brightness update failed` → 明确失败，检查 `E:\.kobo\Kobo\Kobo eReader.conf` 是否存在/是否只读。
  - 色温**不会**写进原生配置（release 明确「色温不写原生配置」），不要据此判失败。

### 4.3 深睡是否真的进到内核（四联判据；入口行 `invoked arg=suspend` **不是**通过依据）
- **前置**：做过 1.4（合盖）或 2.1（电源键）的锁屏动作，且**整轮在拔掉 USB、电池供电下完成**。
- **操作步骤**：锁屏 / 合盖 → 保持拔线直到唤醒 → 退出 Reeden 回原生主页 → 再插 USB → 取 `power.log`（日志追加写入，不会丢）。
- **期望现象**：同一次 Attempt 内同时满足四条：① `[power] entering mem`；② `[power] mem returned=0`；③ `phase=suspended` 与 `phase=resuming` 两行的 `uptime=` 相减 **> 5 秒**（不是 `preparing`→`resuming`，那含准备阶段）；④ 全程无 `[power] screen-only: supply guard`，且 `helper exiting=0`。
- **看哪份日志 / 哪一行**：`power.log` → `phase=preparing uptime=N pid=N`（按 pid 配成一次 Attempt）→ `entering mem` → `phase=suspended uptime=` → `phase=resuming uptime=` → `mem returned=0` → `helper exiting=0`。
  **为什么入口行不能当依据**：`[power] invoked arg=suspend` 由 `power.sh:7` 在脚本入口**无条件打印**，只要宿主以 `suspend` 调用就必有此行；而 `power.sh:89` 的供电保护在 USB 充电 / 非 `Discharging` / `external=on` 时打印 `[power] screen-only: supply guard` 后**直接 `exit 3`**，设备只锁屏、从未进内核。验收又必须插 USB 才能读 `power.log`，所以「见到 `invoked arg=suspend` 就算过」在插线场景下**必然假阳性**——这条判据已被仓库 `docs/实机验收清单-v0.7.9-community.4.md` 第 4 节明确废止。
- **失败怎么办**：
  - 只有 `screen-only: supply guard` → **不算失败**，是设计内的供电保护。改为**拔线电池供电**重做，并保持拔线直到唤醒；插着 USB 的会话一律**不判 PASS 也不判 FAIL**。
  - `mem returned=[1-9]` 或 `short mem return after Ns`（`exit 76`，≤5 秒即返回）→ **明确失败**。
  - `display did not become idle`（`exit 75`）/ `existing alarm: suspend cancelled`（`exit 2`）/ `Wi-Fi could not be suspended` → 准备阶段失败，按 1.4 的兜底说明排查。
  - 需要完整四联（含 uptime 跨度、按 pid 配对）时，直接跑仓库 `tools/Check-SuspendGate.ps1 -LogPath <power.log>`：入口行只计数不计分，`screen-only` 判 `NOT_APPLICABLE`，只有四联齐才 `PASS`。

# 第 5 章 控制面板（`.4` 新增，`.5` 沿用）（ID 5.1 ~ 5.4）

> 入口（`system_panel.c:system_panel_pointer`）：从**屏幕顶部中间**（x≈300~772、y≈0~24）向下滑，位移 `dy>=100` 且 `dy>dx+40` 才展开；第二根手指会取消手势。展开时先发一次 `PANEL_PROBE` 查询真实 Wi-Fi 状态。

### 5.1 面板打开与 Wi-Fi 状态探测
- **前置**：Reeden 阅读页、已拿到显示所有权。
- **操作步骤**：从顶部中间向下滑 → 面板出现 → 观察 Wi-Fi 状态文字（已关闭 / 已开启未连接 / 已连接 / 未知 / 处理中 / 错误）→ 点右上角「刷新」再查一次。
- **期望现象**：面板显示当前真实状态，不是固定图标；处理中阻止重复点击。
- **看哪份日志 / 哪一行**：`current.log` → `[wifi] panel helper finished action=1 result=<code>`（`host.c:422`，action=1 即 `PANEL_PROBE`）。`wifi.sh probe` 返回码：`10`=接口未上电 → `PANEL_OFF`；`11`=上电未连接 → `PANEL_ON`；`12`=已连接 → `PANEL_CONNECTED`（`wifi.sh` + `system_panel.h` 枚举，host 用 `code-9` 映射）。`result` 非 10~12 时状态记 `PANEL_UNKNOWN`。
- **失败怎么办**：`action=1` 且 `result` 异常 → 看 `logs/wifi.log` 的 `[wifi] request=probe ...`；面板显示「错误」时点「刷新」。缺少 NickelDBus 只影响**返回原生后的同步**，不影响面板内真实开关。

### 5.2 Wi-Fi 真实开关
- **前置**：5.1 面板已打开且状态不是「未知」。
- **操作步骤**：点 Wi-Fi 开关 → 观察设备真实无线状态变化（原生系统里核对 / 观察是否能连已保存网络）→ 再点回来 → 点「刷新」核对。
- **期望现象**：真实开启/关闭 Kobo 无线接口；状态在「已关闭 / 已开启未连接 / 已连接」间变化；不显示、不记录密码。
- **看哪份日志 / 哪一行**：`current.log` → `[wifi] panel helper finished action=2 result=0`（`PANEL_WIFI_ON` 成功）/ `action=3 result=0`（`PANEL_WIFI_OFF` 成功）；`logs/wifi.log` → `[wifi] request=on|off <UTC date>`、`[wifi] radio off`、`[wifi] already connected`、`[wifi] association/DHCP started; connection is not yet assumed`。
  **判读边界**：`result=0` 只证明命令执行成功；「接口已开启」**不等于**已连热点或能上网（release 原文）。真实硬件状态需人工核对，脚本在日志层面给 PASS 并附此提示。
- **失败怎么办**：`result` 非 0 → 看 `wifi.log` 的 `[wifi] stale supplicant did not exit` 等；首次连接新热点仍须在**原生系统**完成。返回原生后不沿用选择 → 检查是否已装 NickelDBus（未装时记为「未同步」，属已知限制，不是缺陷）。`userdata/wifi-handoff=keep` 表示交接时保持无线电供电（默认 `default` 是断电交接）。

### 5.3 「立即锁屏」
- **前置**：5.1 面板已打开。
- **操作步骤**：点面板左下「立即锁屏」按钮 → 屏幕灭、前光灭 → 静置后按电源键或开盖唤醒。
- **期望现象**：与电源键/合盖同样的锁屏流程，且**不要求有保护盖**。
- **看哪份日志 / 哪一行**：`current.log` → `[power] screen locked; engine retained`（`host.c:490` 收到 `PANEL_LOCK` → `set_sleep(true)`）；`power.log` → `[power] invoked arg=suspend` → `[power] entering mem` → `[power] mem returned=0`。
- **失败怎么办**：同 1.4 / 2.1 的兜底清单（供电保护、显示忙、8 秒重试）。面板显示「传感器暂不支持」时**本来就该用这个按钮或电源键**。

### 5.4 「返回阅读」与右上角关闭（人工观感项）
- **前置**：5.1 面板已打开。
- **操作步骤**：点「返回阅读」或右上角关闭按钮 → 回到原阅读页；翻一页再打开面板确认没有旧截图盖回页面。
- **期望现象**：面板消失、恢复**最新**阅读画面，不把旧截图盖回页面（release 明确此项）。
- **看哪份日志 / 哪一行**：无对应自动日志（`system_panel.c` 里只是 `shown=false`，不发 action），脚本固定输出 `NEED-EVIDENCE`，需人工在清单上勾选。
- **失败怎么办**：若出现旧画面残留，记录操作步骤与截图，保留 `current.log`；此项纯观感，不能靠日志判 FAIL。

# 第 6 章 隔夜功耗取证（ID 6.1 ~ 6.2）

> **重要边界**：release 原文「`mem` 返回成功或前后相隔数小时，不等于测得真正低功耗」。本章只做**取证方法**，不宣称测得低功耗。官方 `scripts/standby_report.py` 是电脑端只读汇总工具，需 Python 3.10+；本包不依赖它。

### 6.1 隔夜休眠阶段记录完整
- **前置**：设备**脱离 USB**、电池供电、电量充足；记下开始/结束的北京时间。
- **操作步骤**：合盖（或短按电源键）锁屏 → 静置整夜（≥ 6 小时）→ 开盖/按键唤醒 → **不要重启 Reeden**，立刻跑 `Collect-Evidence.ps1`。
- **期望现象**：`power.log` 里同一 PID 的一次尝试具备完整阶段链：`phase=preparing` → `phase=suspended` → `entering mem` → `phase=resuming` → `mem returned=0`，且 `suspended` 与 `resuming` 的 `uptime` 相差数小时。
- **看哪份日志 / 哪一行**：`power.log`（`power.sh` 的 `power_phase`，注意与 `current.log` 里 `host.c` 的 `[power] phase=... wall=... mono_ms=...` **格式不同、文件不同**）→
  `[power] phase=preparing uptime=N pid=N <UTC date>` / `[power] phase=suspended uptime=... pid=...` / `[power] phase=resuming uptime=... pid=...` / `[power] phase=complete ...`；
  `[power] entering mem <UTC date>` / `[power] mem returned=0 <UTC date>`；
  合盖/开盖边沿另看 `current.log` 的 `[power] phase=cover-closed|cover-opened wall=<UTC epoch秒> mono_ms=...`。
- **失败怎么办**：阶段链中断先看 `[power] helper exiting=<非0> <date>`（准备阶段退出码）、`screen-only: supply guard`（充电中只锁屏）、`display did not become idle`、`short mem return after Ns; wake source unknown`（`exit 76`，异常短暂返回）。**`power.log` 超 256 KiB 会被轮转成 `power.log.1`**，长测后一起保留。

### 6.2 隔夜电量取证（人工记录项）
- **前置**：6.1 完成。
- **操作步骤**：记录睡前/醒后的电池百分比（设备 UI 读数），与日志里的 `capacity` 对照；如可用，在电脑端对已复制的 `power.log` 跑 `python -B scripts/standby_report.py --log .\evidence\power.log` 做只读汇总。
- **期望现象**：日志 `before_mem` / `after_mem` 的 `capacity` 变化与设备 UI 观感量级一致，无异常掉电。
- **看哪份日志 / 哪一行**：`power.log` → `[power] sample=before_mem battery=... external=... capacity=N` 与 `[power] sample=after_mem ... capacity=N`（`power.sh:power_sample`）。`standby_report.py` 会解析这两行并给出电量读数差。
- **失败怎么办**：脚本对此项固定输出 `NEED-EVIDENCE`（真实耗电量必须人工读数，日志只是脚本尝试记录、不是最低功耗驻留时间）。若 `capacity` 缺失或 `sample` 行不全，说明日志被轮转/被截断，补取 `power.log.1`。异常掉电要保留完整原始日志，但**不要**据此宣称「隔夜功耗已验收」——官方明确本版尚未完成该验收。

## 附：判读结果对照

脚本对第 1~6 章共 **19 个检查项**输出 `PASS` / `FAIL` / `NEED-EVIDENCE` 三态，并附命中的原始日志行（带文件名与行号）。**证据不足一律 `NEED-EVIDENCE`，不判 `FAIL`**；只有出现明确反证（`mem returned` 非 0、`no first frame in 20s`、`Nickel brightness update failed`、驱动 `submission failed` 等）才判 `FAIL`。纯观感项（3.3 / 5.4 / 6.2）固定 `NEED-EVIDENCE`，需人工在清单上勾选。

汇总与退出码：`0` 全 PASS；`1` 有 NEED-EVIDENCE 无 FAIL；`2` 至少一项 FAIL；`3` 找不到证据源。
